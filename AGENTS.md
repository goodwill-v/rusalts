## 1. Главный принцип

**Git — единственный источник правды. Сервер — только деплой. Агент — только ветка.**

- Никто (включая OCLAW) не правит прод-сервер в обход git.
- Всё, что должно попасть на сайт, сначала попадает в git, потом — через автодеплой на сервер.
- Прямые правки на сервере в обход git — запрещены (это теряет работу: файлы не попадают в сборку).

## 3. Структура репозитория (зоны)

Монорепо: один репозиторий, несколько зон по папкам. Зоны **не закреплены жёстко**
за агентами — задачи могут пересекаться. Зона нужна, чтобы понимать, что где лежит.

| Зона | Папки | Примеры задач |
|------|-------|---------------|
| **Сервисы / Услуги** | `app/routers/`, `app/templates/`, `app/static/` | Витрины, страницы услуг, тарифы, боты |
| **Диагностика** | `app/diagnostics/` (новая зона) | Онлайн-диагностика У0–У4, маршрутизация |
| **Контент** | `parser/`, `knowledge_base/`, `content-воркеры`, `talk/` | Парсинг, новости, статьи, VK, каналы |
| **Инфраструктура** | `deploy/`, `Dockerfile`, `docker-compose*.yml`, `.github/workflows/` | Деплой, nginx, CI/CD |
| **Документация** | `README.md`, `docs/`, `AGENTS.md` | Описания, инструкции |

## 4. Стандарт коммитов

- **Язык сообщений:** русский (для читаемости Шефом).
- **Формат Conventional Commits** (тип + зона + суть):
  - `feat(услуги): карточки тарифов на /techologis/`
  - `fix(контент): кодировка в парсере VK`
  - `docs(диагностика): описание У0–У4`
  - `chore(инфра): staging-конфиг`
- **Один коммит = одна логическая правка.** Не смешивать несвязанное.
- Секреты, пароли, токены, ключи — **в коммиты не попадают никогда** (см. §7).

## 5. Цикл работы над задачей

```
Задача из доски/плана
  → 1. git pull (свежий main)
  → 2. git checkout -b feat/<зона>-<кратко>   (новая ветка)
  → 3. Правки + коммиты (несколько, по логике)
  → 4. git push (ветку на GitHub)
  → 5. Создать Pull Request (PR) в main
  → 6. CI (pytest) — должен стать «зелёным»
  → 7. Мёрж в main (L2 — по согласованным задачам)
  → 8. Автодеплой на прод (GitHub Actions сам)
  → 9. Отчёт Шефу: что сделано, ссылка на PR
```

**Именование веток:** `feat/услуги-тарифы`, `fix/контент-кодировка`, `docs/агенты-правила`.

## 6. Уровни автономии (L1–L4)

| Уровень | Что можно | Кому |
|---------|-----------|------|
| L1 | Коммиты в свою ветку, открыть PR | Всем агентам, без спроса |
| L2 | Мёрж в main при зелёном CI (по согласованным задачам) | Всем агентам |
| L3 | Деплой на staging | Всем агентам (после настройки контура) |
| L4 | Деплой на прод напрямую | Только Шеф (релиз тегом) |

- **L2 работает только для задач из согласованного плана.** Новая/незапланированная
  работа → сначала предложение Шефу, потом код.
- Релизы на прод — тегами `vX.Y.Z`, решение принимает Шеф.

## 7. Секреты и безопасность

- Секреты хранятся **только** в `.env` на серверах и в GitHub Secrets.
- `.env`, ключи, токены, пароли — в git **запрещено** (файл `.gitignore` уже защищает).
- Если агент видит секрет в коде/коммите — немедленно сообщить Шефу.
- Каждый агент работает со **своим** токеном GitHub (fine-grained PAT, только репо
  rusalts, права Contents+PR). Отозвать один токен — не трогая других.

## 8. Стоп-условия (когда НЕЛЬЗЯ мёржить/деплоить)

1. CI «красный» (тесты упали) — не мёржить, чинить.
2. Задача вне зоны/плана — только предложение, не трогать код без согласования.
3. Миграции БД, изменение инфраструктуры, секретов — только Шеф.
4. Неизвестный файл/правка в чужой зоне — спросить, не перезаписывать.
5. Прямой пуш в main (в обход PR) — запрещён (защита ветки).
6. Форс-пуш, переписывание истории — запрещены.

## 9. Автодеплой (как устроено)

- Пуш в `main` → GitHub Actions: CI (pytest) → Deploy (rsync + docker compose на сервере).
- Прод: `https://rusalts.ru` (Timeweb Cloud).
- Staging (черновик для проверки): отдельный контур, разворачивается из ветки
  `staging` (после настройки, см. `deploy/STAGING.md`).
- Если деплой упал — агент, чей коммит вызвал падение, чинит первым.

## 9.1 Staging — адреса и как показывать Шефу

- Staging живёт на том же сервере, но **отдельно** от прода (свой порт/поддомен, свои данные).
- **Ссылку на staging можно и нужно давать Шефу в чате** — он открывает её прямо в дашборде, это удобно.
- Адреса:
  - `http://109.73.202.123:8001/` — черновик по IP (HTTP, без замка) — для быстрой проверки;
  - `https://staging.rusalts.ru/` — черновик с HTTPS (после настройки домена) — для международного агента CLAUD (он может смотреть и править сам).
- При передаче ссылки Шефу — указывать, что это **черновик**, и что именно смотреть (страница/функция).
- Прод-ссылка `https://rusalts.ru` — для клиентов; в чат с Шефом давать только когда речь о боевом.
